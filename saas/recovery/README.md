# Live payment and recovery gates
Live billing remains disabled in the shared database. No Stripe account, checkout session, webhook endpoint or real payment exists. The offline signature verifier accepts only raw bytes, expected API version and mode, checks time and HMAC. Prefer Stripe's official SDK at deployment. A signature is not eligibility evidence: the trusted handler must independently retrieve the event, invoice/payment, subscription, customer, account and product/price from Stripe's API; reject out-of-band/manual payments, discounts/prorations, currency/amount mismatch and unpaid/refunded/disputed invoices. Map refunds/disputes to revocation of the exact invoice; handle replay, retry, expiry, cancellations and reconciliation. Only a separate server with a restricted secret may invoke the service boundary. Never enable the database live switch until end-to-end sandbox and legal/provider eligibility checks pass. The provider choice is provisional; no credentials in chat or source.
Recovery: capture database dump, complete Storage archive and config privately with a supported authorized process. Run `RECOVERY_KEY_HEX=<private 64 hex> node saas/recovery/bundle.mjs pack /private/capture /private/new-bundle <UTC timestamp>`, then `node saas/recovery/bundle.mjs verify /private/new-bundle` with the same private environment key. Store key independently in an approved vault. The tool streams AES-256-GCM authenticated encryption and verifies hashes, not dump completeness or restoration. No cloud access, capture, restore or schedule occurs. Never restore into original/control/other existing projects. Restore to independently inventoried empty isolated environment, compare schema, rows, RLS, Auth, Storage, permissions and application tests; preserve evidence, only authorized verifier inserts backup evidence. Shard release plan requires recent verified recovery evidence and may be cancelled on revocation. There is no deploy worker or automatic migration execution. No real backups are recorded.


Artifact extraction: `node saas/recovery/bundle.mjs extract /private/bundle /private/new-extraction` with the same private environment key. The new directory must not exist, must be outside the repository and encrypted bundle, and must have a regular parent. Authenticated decryption checks every byte and removes incomplete output on failure. Extraction alone is not database restoration, and no backup evidence or release approval is created.


`saas/recovery/isolated-drill.mjs` runs in the disposable PostgreSQL 17 GitHub Actions service, creates a synthetic source and target, dumps, encrypts, extracts, restores, compares rows and role/RLS behavior, and checks the fixture Storage archive and config. It is not a restore of the SaaS development or production database and cannot register backup evidence.

## Automated private logical capture
`capture.mjs` is an executable host-side capture pipeline (not activated): dedicated SaaS project guard, Supabase CLI roles/schema/data exports, managed-schema review dump, explicit complete Storage object inventory plus authenticated downloads, size/inventory checks, AES-GCM packaging and verification. Source credentials and recovery key must be provisioned outside the repository. Use Node 22+, Supabase CLI with Docker, compatible pg_dump/psql, tar, a private directory and a non-public recovery host. The private configuration snapshot must identify the source project and exact application commit, and enumerate required deployment configuration without embedding live secret values. Use a genuine maintenance window that freezes database and Storage writes; the confirmation environment variable is not a lock. The three CLI dumps are separate snapshots. Capture fails if Storage changes during capture, but only a write freeze establishes cross-artifact consistency. No retention deletion is automated. Keep a verified off-site copy and independent key custody.

The example systemd service/timer schedules a daily run only after host provisioning and genuine coordinated write freeze; do not install as-is on a live host without this coordination. Backup credentials and environment file must be mode 0600. Do not enable the timer with a permanently hard-coded freeze confirmation. Rotate credentials and revoke on host compromise. A logical capture is not a full managed-platform clone: managed-schema customizations, Vault encryption root keys, auth provider settings, edge functions, DNS, mail and Storage metadata need controlled reconfiguration. Restore only into a new independently isolated project after review, using authenticated extraction via bundle.mjs and the official Supabase CLI restore procedure; never replay managed-schema-review.sql blindly. Verify object inventory, data, RLS, Auth, and operational behavior before any production release. No live capture, scheduler, or restore was executed. See https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore and https://supabase.com/docs/guides/platform/backups.
