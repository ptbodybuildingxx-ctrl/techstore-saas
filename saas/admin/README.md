# Super Admin development
Dedicated control plane only. This UI uses the actual control-plane URL and its **publishable** browser key; no service credentials. Run from a trusted local checkout with `python3 -m http.server 8765 --bind 127.0.0.1` and open `http://127.0.0.1:8765/saas/admin/`. Use a dedicated HTTPS origin before hosting. The shop UI is unchanged.
The database migration `../control-plane/admin-development.sql` must be installed after the base control-plane schema. It adds operator-only overview, registration and trial/suspend/cancel/reopen RPCs, plus private audit records. A registration has no project or origin and cannot be marked ready by these APIs. Trial is administrative metadata, not payment or store entitlement.
Create the operator in the dedicated project's Authentication > Users dashboard, verify ownership and email, then add the exact user UUID to saas_private.operators as an administrator. MFA remains required by default. A development-only exception may be assigned explicitly to one verified operator by setting mfa_required=false; re-enable it and configure MFA before commercial use. Never grant the role by public signup or user metadata. No real operator is included.
The UI uses a password login and an in-memory session; no persistent credentials or refresh token. It requires a fresh login after expiry. No hosting or MFA enrollment is implemented. The development UI is not authorized for commercial deployment. Payment, tenant projects, real license enforcement, backups and restoration require separate work. 
Run `npm run verify` in Node 24. The branch includes the previously tested catalog-isolation fix; no merge or publication is authorized by this development stage.

## Provisioning and entitlement development
Apply `../control-plane/provisioning-entitlement.sql` after admin development. Privately populate protected_projects with every existing non-tenant project ref before any provisioning integration; never put unrelated private refs in Git. Queue requests are idempotent, cancel on suspension, and do not create cloud resources or authorize spending. There is no automatic worker or approval route. The service-only trial decision requires a matching ready project, an unexpired trial and a verified, unrevoked grant. No grants are issued automatically, no paid entitlement is supported, and no store-side enforcement is connected. The browser shows only pending/blocked status, not an active operational license.

## Development username activation (no personal email required initially)
Apply admin-setup.sql and admin-contact.sql in the dedicated control plane. The intended username is king. For development only the login maps to the non-deliverable reserved alias king@techstore-admin.invalid. The project owner must create a NEW user with that alias and choose a strong password privately via the Supabase Auth Users dashboard, using admin confirmation for the internal alias only. If that address already exists, stop: do not authorize a pre-existing signup. The owner must verify the UUID of the exact user they created before explicitly binding that UUID to the private operators table; no automatic name-based authorization is allowed. Do not store passwords in Git or send them in chat. If the Auth dashboard rejects the reserved alias, stop and use another supported verified login method. The UI accepts king and the password. The operator contact RPC allows the logged-in operator to add an optional unverified contact email; it is not an Auth identity or a recovery address. Never use it for access control. Actual verified recovery, MFA and commercial sign-off remain separate gates. The alias cannot receive mail, and a lost password requires project-owner intervention. No real user is seeded.

## Central update planning
Apply `../control-plane/provisioning-revocation.sql` after provisioning-entitlement.sql and `../control-plane/release-planning.sql` after the protected-project registry exists. The development console records immutable version manifests (Git commit, bundle SHA-256, migration SHA-256, notes and rollback plan), and one cancellable plan per ready independent shop. Suspending or changing the shop target invalidates its plan. Protected projects cannot be targeted. No files are fetched, verified or applied by this module. Before implementing a worker: verify signed manifests, inspect migration compatibility, independently verify backup and restoration, use isolated canary stores, require explicit approval, revalidate target identities, record observed before/after versions and health checks, and stop on failure. Never automatically undo destructive migrations or overwrite live data. No commercial deployment or restoration is implemented.

## Backup coordination and release gate
Apply `../control-plane/backup-coordination.sql` after release-planning.sql. Update plans now require independently recorded evidence for the same store/project/origin, a capture within 24 hours, and a successful isolated restore drill. Prior planned records are cancelled at migration; revoking or changing evidence cancels dependent plans. An expired plan is never permission to execute; a future worker must revalidate the exact linked backup at execution time. Backup/restore drill requests do not create artifacts or perform restores. No browser or service role can approve evidence. The catalog contains digests and timestamps, not secrets or backup files. Before a trusted verifier records evidence: capture a consistent database snapshot and separately export Storage files and configuration, encrypt artifacts outside the project, verify checksums, restore to a disposable independent environment, compare schema and row counts, validate authentication/permissions and file manifests, and record test evidence. Never restore to a live store or to a protected project. This is a conservative development policy, not a production backup SLA. Real backup automation, independent restore drills and secure offsite storage remain required.
