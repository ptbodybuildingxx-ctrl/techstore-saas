# Shared tenant foundation
Apply 001-shared-foundation.sql after control-plane billing sandbox on the dedicated SaaS project only. The original shop migrations assume one singleton workspace and must not be installed here. Each store gets a UUID and private membership. Product primary key is (store_id,id), SKU uniqueness is (store_id,sku), ledger foreign key includes store_id, and request IDs are unique per tenant. RLS checks live session and membership; the platform operator has no automatic operational rights. Product changes are limited to owner/stock on an unexpired development trial. Cashier/tech may read products but not the stock ledger. No direct client writes or service-role grants. Suspended tenants retain authorized read access for eventual export. All tests use rolled-back fixtures.
The administrative registration route requires a separately confirmed Auth user, not an arbitrary email claim. Shared stores cannot request dedicated cloud projects or be assigned a project ref. Legacy administrative trials are reused for this limited development phase. No commercial license, real owner, actual storefront, or payment is provisioned.

## Placement directory and scaling
Apply 002-shard-directory.sql after 001. Each workspace receives a single immutable placement on shared-001 (current project); all new group registrations are planning records only. Move plans are idempotent and generation-bound, cancel on closure and cannot execute. Local reads are checked against local placement and membership. The operator directory and tenant product listing have bounded keyset pages (up to 100); group list is capped at 100 in this development API. Existing global admin search/counts are not yet scale-optimized. No remote credentials, databases or routing gateway exist. Future implementation requires partition/index analysis on representative workloads, central Auth trust, private server routing, verified tenant export/import and row/file reconciliation, write fencing and atomic generation cutover, rollback and chaos tests. The 100,000-tenant goal is a design target, not tested capacity; measure peak concurrency, operations, storage, resource limits, and latency before choosing shard sizes. No new paid resources.

## Cash sales foundation and pilot UI
Apply 003-sales-cash-ledger.sql after 002. A store owner explicitly selects SEK, EUR or USD for the development store; the currency cannot change, and monetary values are integer minor units. Owner sets price; owner/cashier records cash-only sales; prices, stock, invoice number, line snapshots, stock events and cash receipt are calculated and committed atomically. Request IDs are scoped to the tenant and replays require the identical normalized cart and actor. Owners can read their shop's sales and cash receipts; cashiers see their own sales only. Suspended stores remain readable to authorized members but cannot sell. No actual money is transferred, and the receipt is not a legal/tax invoice. No VAT, refunds, discounts, cost accounting, customers, installment payments or complete original module parity yet. Store-level locking serializes development writes per shop; measure and optimize concurrency before production.
Run the local static server from the repository root, open /saas/tenant/ and use a confirmed member account (not king) for an explicitly registered development trial. This pilot is separate from original UI. Product and sales pages are bounded. Pending sale IDs are retained in memory during uncertain retries; do not reload or repeat a new sale without checking the sales log. Durable offline queue and full browser/real-user testing are still required. No real tenant accounts have been created. The preceding SQL tests used rollback fixtures only.
