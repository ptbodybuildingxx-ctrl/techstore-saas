# Shared tenant foundation
Apply 001-shared-foundation.sql after control-plane billing sandbox on the dedicated SaaS project only. The original shop migrations assume one singleton workspace and must not be installed here. Each store gets a UUID and private membership. Product primary key is (store_id,id), SKU uniqueness is (store_id,sku), ledger foreign key includes store_id, and request IDs are unique per tenant. RLS checks live session and membership; the platform operator has no automatic operational rights. Product changes are limited to owner/stock on an unexpired development trial. Cashier/tech may read products but not the stock ledger. No direct client writes or service-role grants. Suspended tenants retain authorized read access for eventual export. All tests use rolled-back fixtures.
The administrative registration route requires a separately confirmed Auth user, not an arbitrary email claim. Shared stores cannot request dedicated cloud projects or be assigned a project ref. Legacy administrative trials are reused for this limited development phase. No commercial license, real owner, actual storefront, or payment is provisioned.

## Placement directory and scaling
Apply 002-shard-directory.sql after 001. Each workspace receives a single immutable placement on shared-001 (current project); all new group registrations are planning records only. Move plans are idempotent and generation-bound, cancel on closure and cannot execute. Local reads are checked against local placement and membership. The operator directory and tenant product listing have bounded keyset pages (up to 100); group list is capped at 100 in this development API. Existing global admin search/counts are not yet scale-optimized. No remote credentials, databases or routing gateway exist. Future implementation requires partition/index analysis on representative workloads, central Auth trust, private server routing, verified tenant export/import and row/file reconciliation, write fencing and atomic generation cutover, rollback and chaos tests. The 100,000-tenant goal is a design target, not tested capacity; measure peak concurrency, operations, storage, resource limits, and latency before choosing shard sizes. No new paid resources.

## Cash sales foundation and pilot UI
Apply 003-sales-cash-ledger.sql after 002. A store owner explicitly selects SEK, EUR or USD for the development store; the currency cannot change, and monetary values are integer minor units. Owner sets price; owner/cashier records cash-only sales; prices, stock, invoice number, line snapshots, stock events and cash receipt are calculated and committed atomically. Request IDs are scoped to the tenant and replays require the identical normalized cart and actor. Owners can read their shop's sales and cash receipts; cashiers see their own sales only. Suspended stores remain readable to authorized members but cannot sell. No actual money is transferred, and the receipt is not a legal/tax invoice. No VAT, refunds, discounts, cost accounting, customers, installment payments or complete original module parity yet. Store-level locking serializes development writes per shop; measure and optimize concurrency before production.
Run the local static server from the repository root, open /saas/tenant/ and use a confirmed member account (not king) for an explicitly registered development trial. This pilot is separate from original UI. Product and sales pages are bounded. Pending sale IDs are retained in memory during uncertain retries; do not reload or repeat a new sale without checking the sales log. Durable offline queue and full browser/real-user testing are still required. No real tenant accounts have been created. The preceding SQL tests used rollback fixtures only.

## Multiple sale currencies (current policy)
Apply 004-supported-currencies.sql then 005-multi-currency-sales.sql. SYP, USD and EUR replace SEK. Each shop may enable all three, with the first selected as its default. Store one independent price per product/currency; stock is shared inside the shop, not duplicated across currencies. A sale has one explicit currency and one immutable request ID; the same ID with a different currency is rejected. Old single-currency write endpoints are revoked. Legacy price values are copied to the original currency without relabeling. In the pilot each currency uses integer hundredths (two decimal places) and existing price limits; no conversion rates, currency redenomination, mixed tender, reporting-currency conversion or FX gain/loss calculations are implemented. Cash receipts retain the sale currency. Do not sum currencies. Subscription billing remains sandbox USD. Prior single-currency description is historical; the updated tenant UI uses explicit currency RPCs. SQL assertions used rolled-back fixtures only.

## Cash movements (006)
Cash balances and append-only movements by currency. Cash receipt insertion posts exactly one movement and adjusts balance atomically with stock and sale. Owner records funding (not profit), expense, or actual exchange with both amounts; the exact ratio is represented by the two integer amounts. No money is transferred and no live market rate or base-currency P&L is claimed. Negative balances are rejected. Owner-only read/write with live trial for writes; suspended reads retained. The UI retains uncertain requests in memory only. No durable queue, correction/reversal workflow, mixed tender, accrual accounting, tax invoices, COGS, debt/installments or production reconciliation yet. Existing test fixtures were rolled back.

## Customers and installment receivables (007)
Apply 007 after cash movements. Owner-only customer records and interest-free credit sales. Each sale selects one customer and one currency; the initial deposit can be zero and only the actual cash collected is posted. The remainder is allocated to 1–60 monthly installments anchored on the first due date; integer rounding is allocated to the earliest installments. Subsequent payments are allocated oldest-first with exact currency, bounded outstanding amount and immutable payment request identity. Credit and cash sales share a common transactional stock and invoice core; retries cannot change payment mode or credit terms. Cash collections are linked to payment IDs and recorded in the same transaction. Existing cash sales remain unchanged. Pilot UI displays customer/debt pages and schedule; pending requests retained only in memory, so verify by reference before a fresh retry after session loss. No interest, mixed currency settlement, loan service, external payments, refunds, collection notifications, accounting/tax compliance or complete module parity. Real browser sessions and load tests remain mandatory. SQL assertions used rollback fixtures only.

## Sale returns (008)
One restockable line per return request, owner only. Each return snapshots original sale currency and unit price; original sale and payment records are preserved. Cash sale refund debits the original currency. Credit return reduces remaining debt first, waives unpaid installment portions latest-first without relabeling historical payments, then refunds any excess already collected. Payment allocation now excludes waived amounts. Return, stock increase and financial adjustment commit atomically; insufficient cash or excess quantity rejects the entire request. No damaged goods/quarantine, full basket batch, exchange of items, external refund, tax credit note, or cost/profit adjustment yet. No durable retry queue; owner must verify uncertain requests before starting another. Browser E2E and concurrent load remain untested. SQL fixtures rolled back. 

## FIFO acquisition costs (009)
Owner-only costed inventory intake, using one currency and exact integer unit cost per batch. Ordinary stock adjustments create unknown-cost layers, never free inventory. FIFO consumption on every negative stock event; returns restore the original sale layers in deterministic order and preserve original costs. Per-sale net revenue after returns, COGS and gross margin are returned only when all remaining units have known costs in the sale currency; otherwise COGS/margin are null (not zero). No silent FX conversion. This is not net profit, tax accounting, supplier payable, procurement payment or cash reconciliation. Stock intake does not debit cash; procurement expenses must be independently recorded and classified, and must not be double counted in future net-income reports. Return layers retain original FIFO order; partial returns assume earliest allocated units returned first. Cost metadata stays private, owner-only RPCs check live membership. Migration refuses historical nonempty stock/event history pending explicit reconciliation; verified current dev database had no records. SQL test fixtures rolled back. Pilot UI not yet browser-tested and pending operations remain in memory only. FIFO reconciliation scans active layers and requires workload/concurrency testing before scale. 

## Operations (010–011)
Purchases use a single product line per receipt, FIFO intake, an optional initial payment and subsequent supplier settlements, one currency per purchase. Supplier payments debit the cash ledger, never ordinary expense; no supplier returns, multi-line bills or purchase taxes yet. Repair ticket tracks customer, device, optional 15-digit IMEI, fault, validated state transitions and immutable events. No repair invoicing, parts consumption or repair warranty workflow. Staff assignment requires a confirmed existing Auth UUID, owner only, no operator or owner escalation; operational staff are not control-plane billing members. Cash-flow report uses UTC dates, per-currency amounts, numeric sums returned as strings, not net income. UI has paginated operational lists and reference-ID forms; requires real browser verification. Test SQL fixtures rolled back. No commercial license or real payment provider. 

## Commerce and accounting (012–016)
Explicit storefront publishing and per-product listing, anonymous catalog exposes only product identity/name/SKU/selected price. Buyer must have confirmed live Auth session; at most 3 pending/10 daily orders per shop/account; pickup only, no reservation, payment or shipping. Owner fulfillment atomically creates actual recorded cash sale and checks current quote/stock. Repair checkout consumes multiple priced parts through FIFO, records service fee, cash receipt, and warranty; direct delivery now requires invoice. Warranty claim transitions are audited; no warranty replacement parts/refund workflow. Mixed cash sale accepts 2–3 distinct currencies, owner-approved immutable manual FX ratios within 24h, exact sum in invoice currency and explicit invoice-currency refund agreement. No change, card tender or mixed credit payment. Period reporting snapshots historical cost/FX, reverses returned costs at return time, and identifies unknown cost. Indicative result after unclassified cash expenses is not statutory net income; no complete accrual/double-entry tax ledger or consolidated currency reporting. All SQL fixtures rolled back. No real orders/charges. Owner UI still pilot; no real browser tests.

## Site builder (022)
Optional versioned site object; legacy design snapshots remain valid. Admin can create up to 8 named pages (32 total typed blocks), render banner, text, image and catalog CTA blocks, assign up to 12 raster JPEG thumbnails to public page elements or product SKUs (50 mappings), and configure separate desktop/mobile catalog layout, columns and spacing. Assets are compressed in the browser, 18,000 base64 characters each, 240 KB total site payload. Publishing intentionally makes all library images public, including unreferenced images. No private uploads, SVG, arbitrary HTML/CSS/JS, external links, or full-resolution media storage. Product image matching uses exact SKU; no automatic SKU rename handling. Pages are in-app tabs, not separately routed/SEO-indexed URLs. Presets for five business categories only populate a sample home page if no pages exist; preserve existing content. Both preview and production pilot use same validated renderer, and all design changes follow existing central-admin draft/publish/version history. A scalable media service, full editor/browser tests and commercial hosting are separate launch gates.

## Purchase batches (023)
Atomic multi-line supplier receipts group existing FIFO purchases into one invoice. Initial cash payments allocate deterministically by product UUID; remaining payments use individual purchase lines. No supplier return or tax adjustment. Admin now reads shared entitlement status, not legacy dedicated-project provisioning. Database migration applied; rollback fixture was blocked by tool and remains an open verification gate.

## Supplier returns (025)
Original intake linkage for each purchase. A return consumes only remaining units of that purchase's layer, reduces outstanding payable first and records cash received for excess only after explicit confirmation; no supplier credit-note or delayed refund receivable. Original purchase/payment values remain unchanged. Batch summaries show net invoice and paid totals. The migration rejects historic unlinked purchases rather than guessing. Rollback tests cover duplicate requests, excess payment, unconfirmed cash refund, specific lot costing, cash reconciliation and tenant isolation. No actual money transferred.

## Operational double-entry (026)
Read-only derived journal pairs from immutable cash, sale, repair, payable, return and inventory events. Period trial balance returns exact opening/debit/credit/closing amounts as strings by currency; unknown cost counts are cumulative through period end. Cross-currency entries use a clearing account, not a consolidated reporting currency. Funding, standalone intake and expenses remain explicitly unclassified. No editable chart of accounts, manual journal, statutory balance sheet, tax, FX revaluation or period locking. Rollback SQL fixture checks cash, inventory, revenue, cost and liabilities, exchange balancing and operator denial.

## Warranty parts and repair settlements (027)
Accepted warranty claims may consume replacement stock at historical FIFO cost, without additional revenue. Repair cash refunds are append-only, limited to the original collected total, with actual payout confirmation and sufficient balance. No automatic restock of used parts, chargeback or real money transfer. Reports include warranty costs and repair refunds; journal excludes warranty consumption from generic shrinkage to avoid double counting. Rollback fixture covers accepted/closed claim boundaries, stock shortage, retry, excess refund, cash, margin, journal and isolation.

## Operational period closing (028)
Owners may close contiguous past UTC periods of up to 366 days, with explicit confirmation. The close saves immutable trial balance, operating and cash reports. Backdated financial inserts are rejected under store lock. Closure rejects unknown historical cost/FX and does not support reopening; future-period corrections only. First closure must include all earlier known journal pairs. Not statutory accounting; unclassified accounts and FX clearing remain. SQL rollback fixture checks current-day denial, overlap, retry, snapshots, current-period writes, backdate rejection, operator isolation.

## Manual delivery (029)
Opt-in, zero shipping fee, manual tracking and cash on delivery. Address/contact restricted to order owner and buyer by existing RLS. Dispatch reserves stock and locks quoted product prices; ordinary reductions cannot consume reserved stock. Owner confirms actual cash on delivery, releasing reservations atomically with the sale. Cancellation after dispatch requires confirmation that all goods physically returned. No carrier API, online payment, route calculation or delivery SLA. SQL rollback tested retry, reservation, price lock, denied buyer dispatch, cash fulfillment and anonymous isolation.

## Closure improvements (030–033)
Subscription plan price changes are audited and permitted only before live billing/bindings. Customer signup, confirmation and recovery adapters are disabled until trusted email configuration is available. Integrated rollback fixture covers purchase batches, sales, returns, repairs, warranty, cash and trial balance. Management statements use one closing-date quote per source currency and explicitly distinguish unclassified balances, before-tax result and missing cost/FX. Not statutory, no jurisdiction-specific tax or final profit. Private JPEG originals use Storage, capped at 12 reservations/store, 100 total and 2 MB/file; actual admin upload and public high-resolution serving remain browser/hosting gates. Coupons apply frozen per-unit integer discount, once per account; loyalty threshold counts prior fulfilled orders not entirely returned. Cancellation releases coupon use, full return does not. No transferable points balance. Page-block drag and drop and page ordering remain declarative, with no arbitrary script or CSS.

## Loyalty points (035)
Owner-configured 2–100 points per reward, discount 1–50%. One point per fulfilled non-reward order not fully returned, including historical eligible orders. A reward order reserves points until cancellation or completion, no combination with coupon, reward purchases earn no new point. Full return of an earning order reverses eligibility and may create a deficit; rewards never convert to cash. SQL rollback checks earning, cancellation, replay, double spend, redemption and return deficit. This order-count model is not a financial stored-value wallet.

## Accounting classifications (038)
Source-bound append-only reclassifications for capital, loans, standalone stock equity, rent/payroll/utilities/other expenses and repayment/withdrawal. Documented income-tax accrual/reversal and actual cash-tax-payment reclassification; no duplicate cash movement. Caps prevent classifying more than source or repaying beyond liability. Management statements include equity, loan/tax liabilities and result after recorded income tax, not statutory profit. No jurisdiction-specific VAT/sales-tax invoice engine, recovery of input tax, tax return or certification. Existing closed-period snapshots are unchanged; current-date adjustments only. SQL rollback checks source cap, replay, equity, liability, tax, balance equation and operator denial.

## Central operational monitoring (039)
Operator-only control-plane summary counts actual shared entitlement, trial/paid, blocked, seven-day expiry, domain registry status, queued recovery/release and local shards with recent verified restore evidence. Up to 100 store IDs per detail request, only aggregate pending/dispatched orders and status flags; no buyer data, transaction values or provider identifiers. SQL rollback verifies trial/pending states and owner denial. Manual refresh; no uptime or real load claim.

## Catalog search and stock history (043)
Server-side literal search by name/SKU across all rows with keyset pagination; public projection includes only listed in-stock products with prices and public string specifications. Owners and stock staff can edit specs under existing write entitlements. Low-stock filter uses a fixed five-unit threshold. Stock history is read-only for owner/stock roles. Deploy migration 043 to the dedicated SaaS database before deploying the matching UI. No branch inventory allocation or external notification delivery is implemented by this migration.

## Receipt snapshots and work alerts (044–045)
Owner receipt settings capture identity, logo, address, phone, titles, format and footer at issuance through insert triggers; original historical lines remain the financial authority. Pre-migration receipts have no invented historical identity. Work alerts are role-scoped derived counts (refresh on load or manually), not push delivery or durable notifications. PC builder uses public specification keys type (cpu/board/ram/gpu/storage/psu/case), socket, ram, form and watts, and reports unknown data rather than guaranteeing compatibility.

## Branch allocation (046)
Branch balances partition existing physical stock; transfers are idempotent and do not double-post cash or FIFO. Cash branch sales use the existing sale engine and branch returns restore branch stock. Main-store stock reductions and order reservations cannot consume allocated quantities. Purchases, credit/mixed sales, repair and delivery still originate in the main store, cost layers remain store-wide, and per-branch staff permissions and financial statements are not implemented. Deploy only after 044–046 pass and dedicated database migration is verified.

## Branch revenue and repair receipts (047)
Owner-only, original sale and return records aggregated by branch/currency and Damascus calendar dates. This is net sales revenue, not profit; no branch-specific expenses or inventory valuation. Repair receipts read original parts, service charges, warranty and issuance identity from the authoritative records.

## Buyer in-app notifications (048)
Live-account scoped inbox records order state transitions and one-shot price-drop/restock watches for listed products, with read state and bounded pages. Watch caps: 30 per buyer/store and 1000 per store. No email, SMS or push transport, no real-time websocket delivery; refresh reads the persisted inbox. Old orders are not backfilled.

## Price quotations (049)
Owner/cashier can save immutable current-price quotes from the POS, valid up to 90 Damascus-calendar days. Server checks product prices, captures receipt identity and retries, and does not post stock or cash. Owner sees all quotes; cashiers see their own. A quote is not a reservation or an issued sale.

## Branch operations (050)
Owner-only branch purchases (single/batch), credit/mixed sales, and repair intake with stock-aware checkout. Supplier returns draw from the original purchase branch. Underlying finance and FIFO engines remain store-wide; online orders and warranty replacement parts still use main stock. No per-branch stock cost valuation.

## Branch cashier scopes and vouchers (051)
Optional single-branch restriction for active cashiers, enforced at sale insertion and branch selection. Unassigned cashiers retain existing store access; stock and technician branch scopes are not implemented. Paid salary, commission, bonus and documented operating expense vouchers post to the existing cash ledger and classification exactly once. Receipt vouchers are explicitly unclassified funding; debt and supplier collections remain in their own flows. No payroll accrual or automatic bank payment.

## Branch management result (052)
Attributed sales, repairs, returns, repair refunds, historical FIFO/FX cost postings, and paid branch operating vouchers by Damascus calendar period and currency. Unknown costs suppress cost and result. Store-wide FIFO, unallocated overhead and tax remain outside branch result; not a statutory branch net profit or separate treasury.

## Customer library (053)
Account/store-scoped favorites and up to 20 saved builds with server-validated snapshot prices and specs. Verified fulfilled online-order customers can submit one review per product; owner moderation is required before public publication. Saved builds are informational snapshots, not reservations. No guest review submissions.

## Marketing and trade-in (054)
Draft/published/completed store campaigns render only during the configured Damascus-calendar dates. Trade-in estimates retain device, condition, accepted value and branch, and can link an actual matching single-unit purchase and sale after acceptance. Linking is documentary, not automatic net settlement or an inventory adjustment. No external campaign delivery.

## Branch staff assignments (055)
Optional single-branch assignment for active cashiers, stock workers and technicians. Assigned cashier/stock catalog reads use own branch balances, direct aggregate product/stock-event access is denied; scoped technicians read/transition own repair tickets. Scoped stock workers may release stock from their assigned branch to main, not allocate from main or modify global products/stock. Owners allocate and adjust. Unassigned staff retain existing store-level roles. Role changes/deactivation clear assignments.

## External delivery (056–057)
Opt-in email and per-shop Web Push queues; retry leases, explicit unsubscribe, private service-only claims. The worker sends only generic account update messages. Setup and scheduling are intentionally disabled; see saas/notifications/README.md.

## Trade-in net settlement (058)
Atomic accepted-estimate settlement uses the existing credit sale and costed purchase engines; an explicit noncash offset balances payable and receivable, and only the confirmed difference posts actual cash. The used device uses a separate product; customer-to-supplier mapping is tenant scoped. Retrying the same request cannot duplicate the sale. Separate returns follow existing return rules (cash refunds may require funds; they do not undo the other leg). Legacy documentary links remain available.

## Product catalog parity (059)
Owner-only create/edit/duplicate metadata, public name/English name/category/brand/model/variant/description/video, up to four compressed JPEG thumbnails, visibility and optional currency price. SKU changes do not rewrite historical sales or stock. Existing design image mappings are SKU-based and may need reassignment after SKU edits. Bulk selected product visibility/brand/category/fixed price; atomic CSV import of new draft products, 100 per file, no stock or cost changes. Public search matches metadata; product detail returns only listed in-stock products and public fields. Photos are bounded thumbnails, not full-resolution storage. Type-specific compatibility still uses existing specs keys. Dedicated migration 059 required before publishing the new UI.

## Storefront and POS availability (060)
Listed, priced products remain visible when unavailable; boolean availability subtracts branch allocations and delivery reservations, without exposing quantities. Category choices populate from the public catalog and submit the existing search (not an exact category filter). Exact POS SKU scanning supports keyboard-wedge readers and validates branch availability. Existing order/sale engines still validate on submission; a catalog display is not a stock reservation. No camera scanning or label printing yet.
