## طريقة تعديل وظيفة

1. اعمل على فرع مستقل قبل تعديل main، واحتفظ بنسخة احتياطية آمنة خارج GitHub.
2. عدّل الوحدة المختصة وأضف اختبارًا. الصلاحيات الحساسة يجب أن تفرض في الخادم/قاعدة البيانات، وليس إخفاء زر فقط.
3. للتغييرات البنيوية في Supabase استخدم migration جديدة ولا تعدّل ملفات مهاجرات مطبقة؛ اختبر البيانات والصلاحيات والتراجع على بيئة معزولة.
4. شغّل npm run verify (يشمل فحص البناء والاختبارات). اختبارات SQLite منفصلة عن Supabase؛ اختبارات الواجهة المحاكاة لا تعني نجاح المتصفح الفعلي.
5. إذا تغير مسار ملف أو أضيف ملف JavaScript، حدّث workspace.html وsw.js وserver.mjs والاختبارات ذات الصلة معًا. فحص JavaScript يكتشف الملفات تلقائياً؛ لا حاجة إلى إضافة اسم كل وحدة إلى package.json. لا تكسر ترتيب defer.
6. وحّد رقم الإصدار في package.json وworkspace.html ومعاملات v في الروابط وsw.js؛ ارفع إصدار ملفات الواجهة والتخزين المؤقت، وافحص GitHub Pages في حاسوب وهاتف بعد النشر. لا ترفع نسخة احتياطية أو مفاتيح سرية.
7. لا تطبق ملفات docs/pending-edge تلقائيًا. هي مقترحات سابقة غير منشورة وتحتاج مراجعة.
8. دوّن الوظائف الناجحة والمحدودة في docs/releases/.

## ملاحظات بنيوية

واجهة JavaScript الحالية تستخدم globals مشتركة وترتيب تحميل ثابت؛ نقلها إلى ES modules أو نظام bundler يحتاج إعادة هيكلة واختبارات مستقلة. تم نقل وحدات الوظائف إلى modules/ دون تغيير أسماء واجهاتها. ملفات النسخة القديمة بقيت في الجذر لأنها تعتمد على مسارات ثابتة. لا تُحذف ملفات المهاجرات ولا يُعاد كتابة سجل Git لإجراء تنظيف شكلي.

## نشر آمن

المستودع عام. مفاتيح publishable مسموحة للواجهة؛ service_role والمفاتيح الخاصة ممنوعة. مراجعة Supabase advisors والاختبارات على الأدوار مطلوبة. لا تستعد قاعدة البيانات من ملف JSON قديم دون مراجعة القيود والسجلات المالية. اختبر النسخ الاحتياطي والاستعادة على قاعدة معزولة.
