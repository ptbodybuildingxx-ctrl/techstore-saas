# النسخ الاحتياطي والاستعادة — TechStore

## الوضع
GitHub يحفظ الكود والترحيلات، وليس نسخة احتياطية من حسابات المحل وبياناته. نتائج اختبارات SQL المنتهية بـ ROLLBACK لا تثبت إمكانية الاستعادة. خطة Supabase المجانية تحتاج نسخاً منطقية خارج المشروع؛ لا ترفع النسخ أو بيانات الاتصال إلى المستودع العام.

## قبل أي تغيير حساس
1. حدد مشروع المصدر ومشروع اختبار مستقل. راجع صلاحيات المالك وتكاليف أي مشروع جديد، ولا تستخدم إنتاج المحل كهدف للاستعادة.
2. استخدم Supabase CLI وفق [دليل النسخ الاحتياطي الرسمي](https://supabase.com/docs/guides/platform/backups) و[دليل الاستعادة](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore). احتفظ بالبيانات والمخطط والأدوار والتخصيصات ذات الصلة، مع خطة منفصلة لملفات Storage وأسرار Edge وإعدادات Auth. لا تنس أن النسخ المنطقية ليست نسخة من ملفات Storage.
3. خزّن الملفات مشفرة خارج Git، وسجّل توقيت النسخة وإصدار الترحيلات وبصمات الملفات. لا تسجل كلمات المرور أو المفاتيح في الوثائق.
4. استعد النسخة في بيئة معزولة مع إيقاف أي إشعارات أو webhooks أو مهام قد تؤثر على الإنتاج. تحقق من الأدوار والتسجيل، عدد السجلات، الفواتير والقيود والمخزون والملفات، ثم نفذ سيناريو بيع وإرجاع ودفعة ومطابقة.
5. وثق النتيجة ومدة الاستعادة والفروقات. لا تعتبر النسخة معتمدة حتى ينجح اختبار الاستعادة فعلياً.

## pg_net
تحذير الموقع في public لا يبرر حذف الإضافة على الإنتاج. وفق [وثائق pg_net](https://supabase.com/docs/guides/database/extensions/pg_net)، الإضافة غير قابلة للنقل المباشر؛ إعادة إنشائها تزيل الجداول المملوكة لها ومنها سجل الطلبات والردود. في المشروع الحالي المالك supabase_admin، والاتصال المتاح لا يملك صلاحياته. اطلب من إدارة Supabase معالجة ذلك بعد النسخ الاحتياطي واختبار التبعيات وإفراغ الطابور والتحقق من الإشعارات. لا تستخدم CASCADE أو تعطّل الإشعارات لمجرد إزالة التحذير.

## معيار الاعتماد
استعادة ناجحة على مشروع منفصل + مطابقة السجلات + اختبار تسجيل الدخول والأدوار والبيع والمرتجعات + تأكيد عدم إرسال إشعارات الإنتاج من نسخة الاختبار.
